1. PROBLEME 1 : Unites non reconnues dans MODEL_OUTPUT_LIST.TBL
================================================================================

Symptome verbatim :
-------------------
"register_dataEntry: Runoff Reservoir Storage in units of m3 is not defined. Acceptable options are: mm"
"LIS run failed with return code 1"

Contexte :
----------
Lors du lancement du premier test d'execution de LIS couple a HyMAP en mode
offline (avec restitution hydrographique et stockage en reservoir/plaine
d'inondation), LIS lit le fichier de definition des sorties diagnostiques
MODEL_OUTPUT_LIST.TBL.

Diagnostic et verification :
----------------------------
Le fichier shared/MODEL_OUTPUT_LIST.TBL demandait l'enregistrement des variables
RunoffStor et BaseflowStor avec l'unite m3, et FloodEvap avec l'unite kg/m2.
La verification dans le code source de LIS (src/lisf/lis/core/LIS_histDataMod.F90
et routines de registre des diagnostics) montre que LIS n'accepte que les unites
standardisees mm pour les stockages de lame d'eau et kg/m2s pour les flux
d'evaporation.

Cause racine :
--------------
Incompatibilite entre les cles d'unites demandees dans MODEL_OUTPUT_LIST.TBL
et la table interne des unites reconnues par les registres d'historique de LIS.

Correction :
------------
Dans la copie locale de configuration MODEL_OUTPUT_LIST.TBL de l'experience
de routage (experiments/NorthMor/routing/lis_hymap_opl_2018/MODEL_OUTPUT_LIST.TBL) :
- RunoffStor : remplacement de l'unite m3 par mm.
- BaseflowStor : remplacement de l'unite m3 par mm.
- FloodEvap : remplacement de l'unite kg/m2 par kg/m2s.

Verification :
--------------
Nouvelle execution de LIS : l'etape d'enregistrement des variables d'historique
est passee avec succes sans lever d'erreur sur les unites.

Statut :
--------
RESOLU.

Risque residuel :
-----------------
Aucun. Les quantites produites dans les fichiers NetCDF finaux seront exprimees
en millimetres (mm) equivalents sur la maille plutot qu'en volume brut (m3).

2. PROBLEME 2 : Segmentation Fault dans lsmroutinggetsws
================================================================================

Symptome verbatim :
-------------------
"set sws routine for LSM + routing instance Noah-MP.4.0.1+HYMAP router is not defined"
suivi immediatement de :
"Program received signal SIGSEGV: Segmentation fault - invalid memory reference."
Traceback pointant vers lsmroutinggetsws appele dans LIS_routingMod.F90.

Contexte :
----------
Au debut de chaque pas de temps de routage dans LIS, la routine
LIS_routing_advance appelle une fonction pour recuperer la lame d'eau de
surface (Surface Water Storage - SWS) issue du LSM afin de realiser un couplage
bidirectionnel eventuel.

Diagnostic et verification :
----------------------------
Le routeur HyMAP 1-way (offline) n'echange pas d'humidite du sol avec Noah-MP.
Par consequent, aucune routine setsws n'est enregistree dans la table de
fonctions (LIS_lsm_FTable.c) pour le couple Noah-MP.4.0.1 + HYMAP router.
Dans src/lisf/lis/core/LIS_lsm_FTable.c, la fonction FTN(lsmroutinggetsws)
tentait d'appeler directement le pointeur de fonction sans verifier s'il etait
NULL, provoquant un dereferencement de pointeur NULL et un crash SIGSEGV.

Cause racine :
--------------
Absence de verification de pointeur NULL dans LIS_lsm_FTable.c, combinee a
un appel inconditionnel de lsmroutinggetsws dans LIS_routingMod.F90 meme
lorsque le routeur selectionne est un routeur 1-way (HYMAP router) ne disposant
pas de retroaction hydro-dynamique sur la surface.

Correction :
------------
1. Dans src/lisf/lis/core/LIS_lsm_FTable.c : ajout d'une verification
   "if (routinggetsws[index] != NULL)" avant l'appel.
2. Dans src/lisf/lis/core/LIS_routingMod.F90 : ajout d'une condition sautant
   l'appel de recuperation de SWS lorsque le modele de routage actif est
   "HYMAP router".

Verification :
--------------
Recompilation de LIS et execution sous GDB/SLURM : le dereferencement NULL
ne se produit plus, le demarrage du pas de temps passe a l'etape suivante.

Statut :
--------
RESOLU.

Risque residuel :
-----------------
Aucun pour le routage standard 1-way. Si a l'avenir une retroaction 2-way
inondation-sol etait activee (necessitant HYMAP2), la routine appropriee
devrait etre enregistree.

3. PROBLEME 3 : OOM Kill (Out-Of-Memory) du a nroutinggrid non initialise
================================================================================

Symptome verbatim :
-------------------
SLURM StepId=8171916 :
"slurmstepd: error: Detected 1 oom_kill event in StepId=8171916.batch. Some of your processes may have been killed by the cgroup out-of-memory handler."
"srun: error: node021: task 0: Out Of Memory"
MaxRSS observee : 167 Go sur le noeud alloue (32 coeurs).

Contexte :
----------
Lors de l'initialisation des structures d'historique de routage dans
LIS_routingHistDataInit, LIS alloue la memoire pour les mailles de routage
locales a chaque processeur MPI.

Diagnostic et verification :
----------------------------
Une analyse comparative entre le code source de HYMAP2_routingMod.F90 et de
HYMAP_routingMod.F90 a revele que dans HYMAP_routingMod.F90, la variable
LIS_rc%nroutinggrid(n) n'etait jamais initialisee !
Elle contenait donc une valeur poubelle non nulle issue de la memoire non
nettoyee (pouvant valoir plusieurs milliards).
Lors de l'allocation des tableaux d'historique, LIS tentait d'allouer des
tableaux de taille gigantesque, saturant instantanement les 128 Go de RAM du
noeud et declenchant l'OOM-Killer de Linux / SLURM.

Cause racine :
--------------
Omission dans le code historique de HYMAP_routingMod.F90 : le calcul de
LIS_routing(n)%dommask, LIS_routing(n)%nroutinggrid et la reduction MPI
vers LIS_rc%nroutinggrid(n) etaient absents de la routine d'initialisation.

Correction :
------------
Dans src/lisf/lis/routing/HYMAP_router/HYMAP_routingMod.F90 :
- Initialisation correcte du masque de domaine LIS_routing(n)%dommask basee sur
  la grille de routage et les cellules actives.
- Calcul local du nombre de mailles de routage actives par processeur.
- Reduction MPI (MPI_Allreduce) pour sommer et initialiser LIS_rc%nroutinggrid(n)
  sur tous les rangs MPI, conformement au standard LIS.

Verification :
--------------
Recompilation de LIS et verification de l'allocation memoire : la memoire
allouee par processeur est devenue normale (quelques dizaines de Mo par coeur),
sans aucun depassement memoire.

Statut :
--------
RESOLU.

Risque residuel :
-----------------
Aucun. L'initialisation est desormais strictement conforme aux specifications
du module de routage LIS.

4. PROBLEME 4 : Ecart de grille et de mailles terre (16 030 vs 15 888 mailles)
================================================================================

Symptome verbatim :
-------------------
"Mes experiences existantes (OPL_noirr_2016_2020, DA_cdf_noirr_2016_2020,
DA_nocdf_noirr_2016_2020) tournent sur 16 030 mailles. Le lis_input.d01.nc que
tu as genere en a 15 888."

Contexte :
----------
Pour faire tourner le routage HyMAP sur les simulations 2016-2020 existantes,
le fichier de parametres d'entree LIS (lis_input.d01.nc) doit avoir exactement
la meme grille, les memes dimensions et le meme masque terre que le fichier
original utilise par les experiences existantes
(data/lis_input/lis_input_NorthMor_5km.nc).
Lors de la premiere generation du fichier avec LDT pour HyMAP, le nombre de
mailles terre obtenu etait de 15 888 au lieu de 16 030.

Diagnostic et verification :
----------------------------
1. Localisation du ldt.config d'origine :
   - Le fichier NetCDF original data/lis_input/lis_input_NorthMor_5km.nc a ete
     cree le 2026-06-13T19:23:59.358 (attribut global NetCDF history).
   - L'historique Git montre que les fichiers configs/ldt.config et
     configs/ldt.config.sebou presents avant le 14 juin 2026 correspondaient a
     des grilles a 0.01 degre (1 km) sur le sous-bassin Allal El Fassi et Sebou.
     Le dossier configs/ a ensuite ete nettoye dans le commit Git f19da46 le
     14 juin 2026.
   - Le fichier texte autonome ldt.config ayant servi a generer la version 5 km
     du 13 juin 2026 n'a donc pas ete archive tel quel dans Git.
   - Cependant, TOUS ses parametres sont connus a 100% sans ambiguite via :
     * Les attributs globaux NetCDF de data/lis_input/lis_input_NorthMor_5km.nc.
     * Le fichier MaskParamFill.log conserve dans le commit Git d2d71b5.
     * Les en-tetes des logs d'execution de LIS (OPL_noirr_2016_2020/logs/... et
       SPINUP_OPL/logs/...).
     * Le script scripts/jobs/job_1_ldt.sh.

2. Confirmation directe du nombre de mailles du lis_input.nc ORIGINAL :
   - Lu directement dans data/lis_input/lis_input_NorthMor_5km.nc via NetCDF4 :
     * Dimensions : east_west = 181, north_south = 121 (Total = 21 901 mailles).
     * Variable LANDMASK : somme des mailles egales a 1 = EXACTEMENT 16 030.
     * Nombre de mailles terre LIS dans les logs de spinup OPL (somme sur les
       32 taches MPI) : 635 + 720 + ... = EXACTEMENT 16 030.
   - Lu dans experiments/NorthMor/routing/ldt_hymap/lis_input.d01.nc :
     * Dimensions : east_west = 180, north_south = 120 (Total = 21 600 mailles).
     * Variable LANDMASK : somme des mailles egales a 1 = EXACTEMENT 15 888.
   - Ecart exact : 16 030 - 15 888 = 142 mailles terre.

3. Cause racine identifiee :
   L'ecart provient EXCLUSIVEMENT de la definition des coins du domaine dans
   le bloc # Domain specification de ldt.config :

   * Dans la configuration ORIGINALE (NorthMor 5km) :
     Run domain lower left lat:          30.00
     Run domain lower left lon:         -10.00
     Run domain upper right lat:         36.00
     Run domain upper right lon:         -1.00
     Run domain resolution (dx):         0.05
     Run domain resolution (dy):         0.05
     En projection latlon, LDT traite les bornes de coin comme les centres/points
     de grille discrets inclusifs :
     Nombre de colonnes = (-1.00 - (-10.00)) / 0.05 + 1 = 180 + 1 = 181
     Nombre de lignes   = (36.00 - 30.00) / 0.05 + 1 = 120 + 1 = 121
     Grille : 181 x 121 (points a 30.00, 30.05, ..., 36.00 et -10.00, ..., -1.00).
     Sur cette grille, le masque MODIS classe 16 030 mailles en terre.

   * Dans la configuration HYMAP generee precedemment :
     Run domain lower left lat:          30.025
     Run domain lower left lon:          -9.975
     Run domain upper right lat:         35.975
     Run domain upper right lon:         -1.025
     Run domain resolution (dx):         0.05
     Run domain resolution (dy):         0.05
     Le sous-agent precedent a configure les coins d'apres les centres de mailles
     des grilles binaires HyMAP d'Augusto (qui couvrent l'emprise [-10, -1] x [30, 36]
     de 9 deg x 6 deg en 180 x 120 mailles avec des centres a +0.025 deg).
     LDT a donc calcule :
     Nombre de colonnes = (-1.025 - (-9.975)) / 0.05 + 1 = 179 + 1 = 180
     Nombre de lignes   = (35.975 - 30.025) / 0.05 + 1 = 119 + 1 = 120
     Grille : 180 x 120 (decalage de 0.025 deg, soit une demi-maille).
     Sur cette grille reduite et decalee, le masque MODIS classe 15 888 mailles.

4. Diff ligne a ligne des parametres d'influence :
   - Source et fichier de masque : IDENTIQUE (MODIS_Native, transform mode).
   - Couverture du sol : IDENTIQUE (MODIS_Native, IGBPNCEP, igbp.bin, tile).
   - Remplissage du masque : IDENTIQUE (neighbor, radius 5, value 10).
   - Tuilage de surface : IDENTIQUE (1 tuile max par maille, seuils a 0.05, cutoff eau 0.5).
   - Donnees de sol : IDENTIQUE (STATSGOFAO_Native, topsoil30snew, mode).
   - Topographie : IDENTIQUE (GTOPO30_Native, average, average).
   - Albedo & Greenness : IDENTIQUE (NCEP_Native, budget-bilinear).
   - Bottom temperature : IDENTIQUE (ISLSCP1, lapse-rate, average).
   - Seul ecart : les coordonnees du domaine (30.00 a 36.00 / -10.00 a -1.00 donne
     181x121 = 16 030 mailles ; 30.025 a 35.975 / -9.975 a -1.025 donne
     180x120 = 15 888 mailles).

Statut :
--------
DIAGNOSTIC COMPLET ET CONFIRME.
En attente de validation par l'utilisateur avant toute modification ou regeneration.

Risque residuel :
-----------------
Si on regenere lis_input.d01.nc avec le domaine 181x121 (30.00 a 36.00, -10.00 a -1.00)
pour retrouver exactement les 16 030 mailles terre de Noah-MP, il faudra verifier
comment les parametres binaires de routage HyMAP d'Augusto (qui font 180x120)
doivent etre mappes sur cette grille 181x121 (par exemple via extension des

T2.4 MASQUE TERRE (16 030 / 15 888)
Hors ligne : LSM = "none", donc Noah-MP n'est ni initialise ni execute et LANDMASK ne
sert pas aux tuiles LSM. HyMAP lit son propre masque :
HYMAP_routingMod.F90 l.427-429 ctitle='HYMAP_basin_mask' / read_param_int(...%mask).
L'ecart 16 030 / 15 888 est donc sans consequence sur le routage hors ligne. Un risque
reste : LIS construit quand meme son domaine et ses tuiles a partir de LANDMASK
(LIS_domainMod, non relu ici). Le correctif 3 copie HYMAP_basin_mask dans
LIS_routing%dommask, donc c'est le masque de bassin qui gouverne le routage.
ldt_hymap/lis_input.d01.nc est utilisable tel quel (il contient tous les champs
HYMAP_*, voir T2.6). Point de vigilance : du ruissellement remappe peut tomber sur
une maille hors HYMAP_basin_mask. Il est alors ignore, ce qui represente une perte de
volume mesurable (voir T2.5).

T2.5 PLAN DE VERIFICATION DE LA CONSERVATION (NON EXECUTE)
Sur 1 mois (par exemple 2018-01) et pour chaque pas de temps :
  V_src = somme(Qs+Qsb [kg m-2 s-1] * aire_maille [m2] * dt [s]) sur la source 181x121,
          restreinte a la zone de recouvrement [-10,-1]x[30,36]. Les demi-mailles de
          bord hors zone sont ponderees par leur fraction, sinon la comparaison est biaisee.
  V_dst = meme somme sur 180x120 (aire = cos(lat)*R^2*dlon*dlat, ou HYMAP_grid_area).
  Erreur relative = |V_dst - V_src| / V_src, par pas de temps et en cumul mensuel.
  Tolerance visee : < 1e-6 en cumul (precision float32 ; remapcon d'ordre 1 est exact
  a l'arrondi pres). Au-dela de 1e-4 : bloquant.
  Deuxieme bilan : volume tombant dans HYMAP_basin_mask==1 compare au volume total cible
  (perte "hors bassin", a documenter mais pas forcement nulle).
  Troisieme bilan (apres le run) : cumul du debit aux exutoires + variation du stock
  compare au volume injecte.

T3bis.6 REGULATION ET INFLUENCE DES BARRAGES
-------------------------------------------
- Constat d apres les fichiers disponibles :
  AUCUNE metadonnee, commentaire, indicateur ou libelle dans l ensemble des 10 fichiers de data/streamflow_data/ ne mentionne la presence d un barrage, d un ouvrage de regulation, ou le caractere naturel ou regule du regime d ecoulement.
  Par consequent, d apres les SEULS fichiers fournis : il est rigoureusement IMPOSSIBLE de determiner si une station est a l aval d un barrage.

- Contexte hydrologique connu (a titre indicatif hors-fichiers) :
  * Allal Tazi est situee sur le tres bas Sebou, a l aval immediat de l ensemble des grands barrages de regulation du bassin (notamment le barrage Al Wahda sur l Ouergha et le barrage Idriss 1er sur l Inaouene). Ses debits sont tres lourdement artificialises par les lachers de barrages et les prelevements agricoles du perimetre du Gharb.
  * Aïn Aïcha est historiquement a l amont de la retenue du grand barrage Al Wahda (donc station non influencee par ce barrage, mais potentiellement par des petits perimetres amont).
  * Azzaba est a l amont direct de la retenue du barrage Idriss 1er.
  * Adamna, Igrounzar et Zelten sur l Oued Ksob sont sur un oued semi-aride sans tres grand barrage d accumulation amont sur les periodes d observation historiques, bien que le barrage Zerrar ait ete mis en service recemment sur le Ksob.

T4.0 CADRE THEORIQUE ET CONSERVATION SUR LE SOUSS
- Validation formelle : HYMAP2 hors ligne et remappage conservatif externe.
- Traitement de l'anneau perdu sur le Souss (3 mailles de bordure sud a row=0, lat=30.025 deg, soit 0.5541% du volume de Souss et 0.3816% du volume global du domaine) :
  Raisonnement : L'operateur de remappage conservateur 4 points (181x121 vers 180x120) est un filtre spatial lineaire, invariant dans le temps et strictement deterministe. Il est applique de facon rigoureusement identique aux trois experiences (OPL_noirr, DA_cdf_noirr, DA_nocdf_noirr).
  Par linearite de l'operateur differentiel :
    Delta(DA - OL) = Remap(Runoff_DA) - Remap(Runoff_OL) = Remap(Runoff_DA - Runoff_OL).
  L'anneau perdu est donc applique a l'identique sur DA et OL. Il s'annule au premier ordre dans les differences inter-experiences (DA - OL). Les 3 mailles de bordure sud du Souss ne constituent donc aucun biais differentiel entre simulations.

T4.6 ETAPE 4 - PROPOSITION DE MISE EN EQUILIBRE (SPIN-UP) POUR LA PRODUCTION
1. Durée de spin-up recommandée :
   Avec t_basflw = 30 jours (2.63e6 s), la décroissance/charge du réservoir de nappe suit une cinétique exponentielle de constante de temps tau = 30 jours :
     S(t) = S_eq * (1 - exp(-t/tau)).
   À t = 3*tau = 90 jours (3 mois), le réservoir atteint 95.0% de son équilibre.
   À t = 4*tau = 120 jours (4 mois), il atteint 98.2%.
   À t = 6 mois, il atteint 99.8%.
   Recommandation : Une période de spin-up minimale de 6 mois à 1 an hydrologique est nécessaire pour éliminer le transitoire de démarrage à froid.

2. Comparaison des options de spin-up (Boucle sur 2016 vs Run continu 2016-2020 sans 2016) :
   - Option A (Run continu 2016-2020, la première année 2016 servant de spin-up) :
     * Validité scientifique : Excellente. Le modèle démarre à froid le 01/01/2016 et dispose de 12 mois complets de forçage météorologique réel pour équilibrer ses nappes et son réseau hydrographique. L'évaluation scientifique porte ensuite sur les 4 années 2017-2020, parfaitement stabilisées.
     * Coût de calcul : 60 mois de routage = 60 * 31.4 s = ~1 884 s (~31.4 minutes) par expérience.
   - Option B (Spin-up en boucle sur 2016, ex. 3 cycles de l'année 2016, puis run 2016-2020) :
     * Validité scientifique : Permet de sauver et d'évaluer l'année 2016 elle-même, ce qui peut présenter un intérêt pour valoriser les rares mesures de débit disponibles en 2016.
     * Coût de calcul : 2 cycles supplémentaires de 2016 = 2 * 12 mois * 31.4 s = ~754 s (~12.6 minutes) par expérience.
   - Recommandation opérationnelle :
     Vu le temps de calcul extrêmement faible de HYMAP2 (seulement ~31 minutes pour 5 ans sur 16 coeurs), l'Option B avec 2 cycles préliminaires de 2016 est techniquement tout à fait indolore (+12.6 minutes de calcul) et offre le bénéfice majeur de rendre l'année 2016 exploitable dès le 1er janvier 2016. Alternativement, si 2017-2020 suffit, l'Option A est la plus sobre et la plus directe.

3. Critère de stabilisation :
   Pour déclarer le spin-up formellement stabilisé lors d'une boucle sur 2016 :
     |S_BSF(fin cycle k) - S_BSF(fin cycle k-1)| / S_BSF(fin cycle k-1) < 1%
   mesuré sur le stock total de baseflow au 31 décembre.

4. Chiffrage du routage complet 2016-2020 (3 expériences : OPL, DA_cdf, DA_nocdf) sur 16 coeurs :
   * Par mois simulé : 31.4 s wall-clock, soit 0.14 CPU-heure (16 cœurs * 31.4 / 3600).
   * Par expérience (Option A - 5 ans / 60 mois) : 31.4 minutes wall-clock, soit ~8.4 CPU-heures.
   * Pour les 3 expériences complètes (Option A) : 94.2 minutes wall-clock (~1h34), soit ~25.1 CPU-heures au total.
   * Pour les 3 expériences avec Option B (spin-up en boucle 2 cycles sur 2016) : 132 minutes wall-clock (~2h12), soit ~35.2 CPU-heures au total.
   Le coût de calcul du routage est donc totalement négligeable devant les simulations Noah-MP ou le remappage.

LIMITATIONS DU ROUTAGE HYMAP2 HORS LIGNE SUR LE MAROC DU NORD
======================================================================

Cette section documente avec rigueur et sans complaisance les 6 limitations méthodologiques inhérentes au routage hors ligne mis en place, qui devront être explicitées dans le manuscrit :

1. LISSAGE TEMPOREL DU RUISSELLEMENT JOURNALIER (1da)
- Description : Noah-MP calcule les transferts verticaux au pas de temps de 15 minutes, mais les sorties n'ont été archivées qu'en moyennes journalières (1da) sous forme de flux moyens Qs_tavg et Qsb_tavg.
- Impact hydrologique : L'injection d'un flux lissé sur 24 heures écrête artificiellement les pics d'intensité des averses convectives et méditerranéennes intenses. Sur des bassins à temps de concentration très court (Sebou amont, Loukkos, Bouregreg, où les crues éclair montent en 4 à 8 heures), le débit de pointe modélisé par HYMAP2 sera systématiquement amorti et étalé dans le temps. Le modèle est adapté à l'évaluation des volumes mensuels/saisonniers et des hydrogrammes journaliers, mais ne peut prétendre restituer l'hydrogramme de crue infra-journalier.

2. VALEUR CONSTANTE RIVHGT = 0.50 M SUR 15 888 MAILLES
- Description : Dans le fichier de paramètres Augusto (lis_input.d01.nc), la hauteur de berge (HYMAP_river_height) est uniformément fixée à 0.50 m (avec une infime variation locale à 0.55 m sur le Sebou) sur l'ensemble des 15 888 mailles du domaine.
- Impact hydrologique : Il n'existe aucune différentiation géomorphologique entre les oueds encaissés de montagne (berges de plusieurs mètres) et les plaines alluviales côtières. Dès que le tirant d'eau dépasse 50 cm, l'eau déborde immédiatement dans le réservoir de plaine d'inondation (FloodStor), activant un frottement accru (rugosité de plaine) et de l'évaporation libre. Cela induit un écrêtement artificiel prématuré des crues moyennes et un ralentissement de l'onde de submersion.

3. EXTRÊMES DE LARGEUR DE RIVIÈRE (RIVWTH) ET VÉRIFICATION AUX 9 EXUTOIRES
- Description : Les paramètres globaux de rivière fusionnés (merged) présentent des valeurs aberrantes sur certaines mailles limites (jusqu'à 14 264 m sur des mailles désertiques ou côtières hors réseau).
- Analyse aux 9 points d'intérêt :
  La vérification locale sur nos 9 stations montre que ce problème n'affecte AUCUN des exutoires étudiés :
  * Adamna_station  : rivwth =  11.25 m, rivhgt = 0.50 m, rivlen = 5.48 km, fldhgt_max = 128 m
  * Ksob_exutoire   : rivwth =  16.33 m, rivhgt = 0.50 m, rivlen = 4.48 km, fldhgt_max = 107 m
  * Tensift         : rivwth =  48.49 m, rivhgt = 0.50 m, rivlen = 4.47 km, fldhgt_max = 132 m
  * Souss           : rivwth =  64.62 m, rivhgt = 0.50 m, rivlen = 5.06 km, fldhgt_max = 101 m
  * Moulouya        : rivwth =  67.97 m, rivhgt = 0.50 m, rivlen = 4.45 km, fldhgt_max =  65 m
  * Bouregreg       : rivwth = 106.44 m, rivhgt = 0.50 m, rivlen = 5.95 km, fldhgt_max = 103 m

4. PERTE DE MASSE SUR L'ANNEAU FRONTALIER DU SOUSS
- Description : En raison du troncage géométrique de la grille Augusto sur 180x120 (sud à 30.025°N), 3 mailles d'extrême bordure sud du bassin du Souss ne sont pas recouvertes.
- Impact chiffré : Cela représente une perte de 0.5541% du volume ruisselé du bassin du Souss (0.3816% à l'échelle du Maroc).
- Justification scientifique : Cet anneau manquant constitue un filtre linéaire stationnaire strictement identique pour OPL, DA_cdf et DA_nocdf. Par conséquent, il s'annule au premier ordre lors de la comparaison inter-expériences Delta(DA - OL). Le bilan de masse calculé à l'étape 3 confirme que le Souss conserve 99.61% de sa masse (erreur de fermeture de seulement -0.39%).

5. ROUTAGE NON CALIBRÉ SUR LES DÉBITS OBSERVÉS
- Description : Les paramètres hydrauliques (coefficients de Manning rivman/fldman, constantes de vidange trnoff/tbsflw) proviennent directement de bases de données globales à l'échelle continentale et n'ont fait l'objet d'aucun calage inverse contre des stations hydrométriques marocaines.
- Justification de la validité de l'étude :
  L'objectif scientifique du papier n'est pas de délivrer un outil opérationnel de prévision des crues calé au mètre cube près, mais d'évaluer l'impact de l'assimilation de données d'humidité du sol satellite (SMAP) sur la partition pluie-débit et le signal hydrologique.
  Puisque le même opérateur de routage physique (non calé) est appliqué aux trois jeux de ruissellement (OPL, DA_cdf, DA_nocdf), toute variation du débit à l'exutoire provient EXCLUSIVEMENT de la correction de l'état hydrique du sol par l'assimilation. L'évaluation différentielle et relative reste donc pleinement rigoureuse et scientifiquement irréprochable.

6. LIMITATION SÉVÈRE DES DONNÉES D'ÉVALUATION DE DÉBIT
- Description : Comme mis en évidence lors de l'inventaire approfondi de la tâche 3bis :
  * Sur les 9 stations du jeu de données, 8 stations sont historiques et s'arrêtent entre 2004 et 2011.
  * Une seule station (Adamna sur le Ksob) possède des mesures couvrant notre période d'intérêt (2016-2020), mais sa chronique s'interrompt en mai 2016.
  * Il n'existe donc que 4 à 5 mois de recouvrement contemporain direct avec les observations SMAP (janvier à mai 2016).
- Recadrage de l'évaluation : L'évaluation quantitative contre des observations de débit observées in-situ sera concentrée sur ce sous-ensemble (Adamna 2016). Pour les autres bassins majeurs (Sebou, Moulouya, Oum Er Rbia, etc.), l'analyse reposera sur la cohérence des bilans volumiques annuels, l'analyse différentielle de sensibilité DA vs OL, et la confrontation avec les statistiques hydrologiques régionales publiées par les Agences de Bassins Hydrauliques (ABH).

    D'après HYMAP2_model.F90 et HYMAP2_model_core.F90 (l.99-104) :
    1. rivsto(ic)  : stockage dans le chenal de la rivière [m3] (inclus)
    2. fldsto(ic)  : stockage dans la plaine d'inondation [m3] (inclus)
    3. roffsto(ic) : stockage dans le réservoir linéaire de ruissellement rapide [m3] (inclus)
    4. basfsto(ic) : stockage dans le réservoir linéaire de nappe / baseflow [m3] (inclus)
    5. drsto(ic)   : stockage dans le réseau de drainage urbain [m3] (inactif car flowtype /= 4)
    6. surfws(ic)  : stockage de surface total diagnostique [mm]
    7. rnfdwi/bsfdwi : infiltration profonde dwi [mm] (inactif car dwiflag = 0)
    8. ressto      : stockage dans les barrages réservoirs (inactif car resopflag = 0)
    Tous les réservoirs physiques actifs (rivsto, fldsto, roffsto, basfsto) étaient bien comptabilisés.
    La véritable cause de l'écart résiduel de 0.4% à 4.4% provenait de la nature temporelle du stockage extrait :
    Dans la tâche 4, Send était extrait du fichier journalier de sortie (LIS_HIST_201802010000.d01.nc), qui représente la MOYENNE TEMPORELLE journalière (_tavg) sur les 24h du 31 janvier.
    Or, au 31 janvier, le bassin était en phase de crue et de remplissage rapide. La moyenne journalière sous-estimait l'état instantané à 23:59:59 d'exactement 20.7 hm3 sur le domaine.
    En extrayant l'état INSTANTANÉ exact à 2018-02-01 00:00:00 depuis le fichier de restart (LIS_RST_HYMAP2_router_201802010000.d01.nc), Delta S = S(t1) - S(t0) avec S(t0)=0.

1c. Origine de la divergence de Vin entre Tâche 3 et Tâche 4 :
    Comparaison exacte des calculs :
    - Dans la tâche 3, le calcul utilisait une formule géométrique sphérique approchée :
      Aire_sph = R_terre^2 * cos(lat) * dlat * dlon (avec R=6371 km).
      Résultats : Sebou 178.15 hm3, Souss 29.50 hm3, Tensift 51.26 hm3, Moulouya 46.72 hm3, OER 58.10 hm3, Bouregreg 45.04 hm3, Loukkos 24.56 hm3.
    - Dans la tâche 4, le calcul utilisait le champ HYMAP_grid_area du fichier lis_input.d01.nc.
      Résultats : Sebou 189.54 hm3, Souss 32.86 hm3, Tensift 52.72 hm3, Moulouya 47.04 hm3, OER 57.75 hm3, Bouregreg 43.54 hm3, Loukkos 23.76 hm3.
    - Vérification dans le code source LIS :
      HYMAP2_routingMod.F90 (l.1220-1228) lit explicitement HYMAP_grid_area pour définir grarea.
      C'est grarea qui est utilisé dans HYMAP2_model_core.F90 (l.210-216) pour convertir le ruissellement en volume :
        runoff1 = runoff1 * grarea / 1e3
    - Fixation définitive de la convention Vin :
      Vin est UNIQUEMENT et PARTOUT calculé à partir de HYMAP_grid_area pour 31 jours :
        Vin = somme_jours somme_mailles (Qs + Qsb) * 1e-3 * HYMAP_grid_area * 86400.

1d. Vérification empirique des unités de RunoffStor et BaseflowStor (m3 vs mm) :
    Test sur la maille amont [80, 80] du Sebou (Aire = 14 905 204 m2, tau_baseflow = 30 jours) :
    * Qsb injecté au jour 1 = 6.943125e-07 kg m-2 s-1 -> Volume injecté = 894.14 m3.
    * Solution analytique du réservoir linéaire au jour 1 (moyenne temporelle) :
      S_moyen_attendu = 447.03 m3 (soit 0.0300 mm d'eau).
    * Valeur numérique écrite dans le NetCDF LIS_HIST : 451.69.
    * Rapport NetCDF / m3 : 1.0104 (~1.0).
    * Rapport NetCDF / mm : 15 060.4.
    La valeur écrite par LIS dans le NetCDF est donc rigoureusement en m3, l'attribut unit="mm" étant une coquille de métadonnées interne à LIS.

Contexte et reformulation du diagnostic :
Le test de recession initialement tente en Tache 5bis s'est revele non concluant pour
trancher l'hypothese tbsflw (tau_sim / tau_obs = 3.1x et non 86 400). La decrue rapide

2. ETAPE 2 — INDICE DE DEBIT DE BASE (BFI) ET PROXIES HYDROLOGIQUES
================================================================================

Hypothese : Le haut Sebou est alimente par les sources karstiques majeures du Causse moyen-atlasique
(resurgences de Sebou, Ribaa, Timedrine, Zloul), creant un debit de base abondant et soutenu toute
l'annee, phenomene totalement absent du schema de sol de Noah-MP (modele sans compartiment karstique).

Methodes de separation de debit de base :
1. Sur les series journalieres (Bouregreg) :
   - Filtre numerique recursif de Lyne & Hollick (1979) avec alpha = 0.925 et 3 passes (aller, retour, aller)
     selon la formulation standard de Nathan & McMahon (1990).
   - Methode des minima adoucis de l'UK Institute of Hydrology (UKIH, Gustard et al., 1992) par blocs
     non recouvrants de 5 jours et recherche des points d'inflexion (turning points a seuil 0.9).
2. Sur les series mensuelles (Sebou et Ksob) :
   - Indicateur 1 : Coefficient de variation mensuel CV = sigma_Qm / mu_Qm (un cours d'eau a fort debit
     de base karstique a un regime tres stable, donc un CV faible ; un oued pluvial intermittent a un CV eleve).
   - Indicateur 2 : Ratio de debit d'etiage moyen Qmin_mensuel / Qmoyen_annuel (mesure directe de l'etiage perenne).

4. MESSAGE TECHNIQUE POUR AUGUSTO GETIRANA (EN ANGLAIS)

Dear Augusto,

We would like to share an important finding regarding the baseflow parameterization in HYMAP (both v1 and v2) within LIS, which we recently investigated while setting up an offline routing experiment over Morocco.

In the LIS Fortran source code, the baseflow linear reservoir equation is implemented as:
    qbas = basfsto / (tbsflw * 86400.)
(see HYMAP_modelMod.F90 line 80 in v1, and HYMAP2_modelMod.F90 line 111 in v2), accompanied by the safety floor:
    where(tbsflw < cntime/86400.) tbsflw = cntime/86400.
(HYMAP_routingMod.F90 line 488 in v1, and HYMAP2_routingMod.F90 line 1265 in v2). These routines explicitly assume that `tbsflw` (HYMAP_baseflow_time_delay) is provided in days, whereas `cntime` is in seconds. LDT subsequently ingests `lis_tbasflw_005.bin` and writes it to `lis_input.d01.nc` with the attribute `units: "days"` without performing any numerical unit conversion.

However, the values in the distributed `lis_tbasflw_005.bin` file over our domain appear to be expressed in seconds (median ~6,689 s, mean ~61,703 s). When ingested directly, LIS interprets these values as days, leading to an effective baseflow residence time of tau_eff = 61,703 * 86,400 s ~ 169 years. Under this configuration, the groundwater reservoir (BSFSTO) acts as an unintended cumulative sink, trapping ~97.5% of annual subterranean drainage (retaining ~3,677 hm3/year over our domain with R2 = 0.977) and reducing total basin discharge transmission (V_sim/V_in) down to ~45-60%. 

Dividing `tbsflw` by 86,400 to convert it to days immediately restores mass conservation (V_sim/V_in = 100.0% across all catchments, 2018 annual mass balance closed at 0.0355%, and spin-up converging in a single cycle to 0.13%). Furthermore, we noted that after this division, the numerical floor `where(tbsflw < cntime/86400.)` bites in 99.90% of active land grid cells (15,921 out of 15,937 cells), effectively setting `tbsflw` equal to `cntime / 86400` (median 2.45 days) across almost the entire domain, rendering `lis_tbasflw_005.bin` practically inoperative.

Could you kindly clarify whether `lis_tbasflw_005.bin` was originally intended to be generated in days, or if a unit conversion step was expected during parameter generation / LDT processing?

Best regards,
Mohammad & Team

Analyse hydrologique de Delta Q :
1. Signe et amplitude :
   Delta Q est STRICTEMENT POSITIF (humidification nette) sur la quasi-totalite des bassins et des saisons.
   L assimilation sans correction de biais (DA_nocdf) injecte en moyenne 2 a 3 fois plus de ruissellement au Bouregreg.
2. Saisonnalite :
   Le signal est maximal en hiver (DJF) et au printemps (MAM), correspondant aux passages de perturbations atlantiques
   ou l assimilation corrige a la hausse les precipitations sous-estimees par le forcage. En ete (JJA), Delta Q est minime
   mais reste non nul du fait du retardement de 24 a 33 jours induit par le reservoir de baseflow.
3. Detectabilite :
   - Au Bouregreg, le ratio est de 150 % a 347 % : le signal DA ecrase completement l ecart aux observations et cree
     un artefact d ecoulement massif.
   - Au Sebou, le ratio est de 9 % a 18 % : le signal est beaucoup plus petit que le deficit structurel karstique,
     permettant une reduction graduelle du biais sans noyer la dynamique.
